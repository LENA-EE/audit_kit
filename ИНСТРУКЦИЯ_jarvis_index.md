# `jarvis_index.py` — одна команда на всю цепочку

Скрипт ведёт индекс кодовой базы от файлов индексатора до живого
импакт-анализа в MCP. Заменяет цепочку из четырёх ручных команд, которые
надо было помнить в правильном порядке.

Написан 2026-09-05 под чанковый формат индексатора v2 (34 файла `chunk_N.json`
плюс `all.json`). Старый однофайловый формат тоже понимает.

---

## Что делает

```
chunk_0.json … chunk_33.json + all.json
              │
              │  merge      склеить в один файл
              ▼
        index.json.gz
              │
      ┌───────┴────────┐
      │                │
      │ db             │ upload
      ▼                ▼
 data/index.db      MCP-сервер
      │                │
      │ report         │ verify
      ▼                ▼
   отчёт.md      кто вызывает функцию
```

Один склеенный индекс — два потребителя. Отчёт по аудиту читает базу
напрямую; MCP принимает тот же файл через свой эндпоинт и собирает базу
у себя внутри.

## Зависимости

Только стандартная библиотека Python 3. Ни `pip install`, ни `curl`,
ни Perl, ни PPI. Заливка в MCP идёт через `urllib` изнутри скрипта.

## Раскладка файлов

```
рабочая_папка/
├── jarvis_index.py            ← запускается только он
├── audit_report.py
├── tools/index_store.py       ← схема SQLite, общая для всех
├── tools/merge_chunks.py
├── tools/load_index_chunked.py
├── all.json                   ← опись от индексатора
└── chunks/chunk_0.json …      ← сами чанки
```

Подкаталог `tools/` обязателен. Пути по умолчанию можно переопределить
флагами (см. ниже), но проще положить как здесь.

## Команды

### `status` — где я в цепочке

```
python3 jarvis_index.py status
```

Главная команда. Показывает, какие шаги уже сделаны, сколько в базе функций
и вызовов, задан ли токен MCP — и какую команду набирать следующей.
Ничего не меняет, запускать можно сколько угодно.

```
ГДЕ Я В ЦЕПОЧКЕ

  [ГОТОВО] 1. чанки            chunks: 34 шт.
  [ГОТОВО] 2. опись            all.json: заявлено файлов 3309
  [НЕТ]    3. склеенный индекс index.json.gz: —
  ...
  Дальше:  python3 jarvis_index.py merge
```

### `merge` — склеить чанки

```
python3 jarvis_index.py merge
```

Собирает `chunks/chunk_*.json` и `all.json` в один `index.json.gz`.

Сверяет результат с `file_count` из описи. Если склеилось меньше заявленного —
печатает предупреждение и возвращает код 2: часть чанков не доехала, дальше
идти нельзя. Ловит и дубли путей между чанками.

`meta` в чанках нет — она берётся из `all.json`. Без описи индекс соберётся,
но останется без даты, имени проекта и числа сбойных файлов; скрипт об этом
предупредит.

### `db` — собрать базу

```
python3 jarvis_index.py db
```

Раскладывает индекс по таблицам SQLite: `functions`, `imports`, `globals`,
`calls`, `meta`. Пишет атомарно — читающие запросы не видят полуготовую базу.

Схема совпадает с той, что создаёт `index_store.load_index()`. Поэтому
`audit_report.py`, `get_callers()` и бот работают поверх результата
без единой правки.

### `report` — построить отчёт

```
python3 jarvis_index.py report
python3 jarvis_index.py report --src /путь/к/чекауту --top 15
```

Без `--src` — уровни 1–2: объём, топ рисков, кандидаты в мёртвый код, циклы,
дубли имён. Чистый SQL, модель не вызывается, токены не тратятся.

С `--src` и переменными `FENIX_URL` / `FENIX_TOKEN` добавляется уровень 3 —
колонка «почему опасна / что делать». Нужен чекаут того же кода на том же хосте.

### `upload` — залить индекс в MCP

```
export MCP_INDEX_TOKEN=...
python3 jarvis_index.py upload
```

Отправляет `index.json.gz` на `POST /index/upload`. Рестарт MCP не нужен:
`tools/list` строится динамически, `get_callers` появляется сразу.

Адрес по умолчанию `http://localhost:8000`, меняется флагом `--mcp-url`
или переменной `MCP_URL`. С самой VM — `localhost`, с другой машины —
имя хоста VM.

Коды ответа переведены на человеческий:

| Код | Что значит |
|---|---|
| 200 | залилось, в ответе `file_count` |
| 401 | неверный токен — сверить с окружением контейнера MCP |
| 404 | в этой сборке MCP нет эндпоинта, нужна версия с `index_store` |
| 400 | сервер не принял тело — индекс побился |
| 503 | на сервере не настроен токен или не подгрузился `index_store` |

### `verify` — проверить импакт

```
python3 jarvis_index.py verify ИМЯ_ФУНКЦИИ
```

Спрашивает у MCP `get_callers` и печатает ответ: из каких файлов и с каких
строк функция вызывается. Если пусто — либо индекс не залит, либо имя другое.

### `all` — merge + db + report подряд

```
python3 jarvis_index.py all
```

Останавливается на первом же шаге, который вернул ошибку. Заливка в MCP
в `all` не входит намеренно: ей нужен токен и она меняет состояние сервера.

## Флаги

| Флаг | По умолчанию | Зачем |
|---|---|---|
| `--chunks` | `chunks` | папка с чанками |
| `--all-json` | `all.json` | опись индексатора |
| `--index` | `index.json.gz` | склеенный индекс |
| `--db` | `data/index.db` | база |
| `--report` | `отчёт.md` | отчёт |
| `--src` | — | чекаут кода, включает уровень 3 отчёта |
| `--top` | 15 | сколько функций объяснять на уровне 3 |
| `--mcp-url` | `$MCP_URL` или `http://localhost:8000` | адрес MCP |
| `--token` | `$MCP_INDEX_TOKEN` | токен заливки |
| `--timeout` | 300 | таймаут запросов к MCP, сек |
| `--force` | — | переделать шаг, даже если он уже сделан |

Повторный запуск сделанного шага безопасен: скрипт скажет «уже собран»
и не станет ничего трогать. Переделать — только явным `--force`.

## Что скрипт не делает

- Не пишет в индексируемый репозиторий и не читает исходный код (кроме
  уровня 3 отчёта, где чекаут нужен явно).
- Не ходит в сеть, кроме адреса MCP при `upload` / `verify`.
- Не требует прав администратора и ничего не устанавливает.
- Не удаляет исходные чанки после склейки.

## Чего в этой цепочке нет

Сборки самого индекса. `build_index.pl` (Perl + PPI) запускается там, где
лежит код, и это отдельный шаг — см. `README.md` и
`ПАМЯТКА_сборка_индекса_и_отчёт.md`. `jarvis_index.py` начинается с готовых
чанков.

## Ограничения, которые видно в отчёте

Наследуются от индексатора, скриптом не лечатся:

- каталоги `t` и файлы вне `.pm`/`.pl` не обходятся;
- вызовы `&func()`, через `eval`-строку и динамическую диспетчеризацию
  не распознаются — раздел «кандидаты в мёртвый код» **завышен**;
- в индексе v2 у большинства файлов `package` = `null` (это нормально для
  скриптов), а отчёт группирует по пакетам — раздел «объём и структура»
  на такой базе выйдет малоинформативным;
- имена функций не разрешаются до полного имени пакета, поэтому
  `get_callers` по частому имени вернёт вызовы всех одноимённых функций.
  Известный пробел, см. `NOTES_impact_analysis.md` §3.

Строка «Покрытие отчёта» под шапкой отчёта говорит, чего в него не попало.
Читать её первой; при показе результата — проговаривать вслух.
